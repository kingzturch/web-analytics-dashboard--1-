# PULSE ANALYTICS - PHASE 3: RELIABILITY, SCALABILITY & DATA INTEGRITY REPORT
**Production Grade Architecture Document v1.0**

---

## 1. CURRENT ARCHITECTURE
Currently, incoming collector HTTP POST requests (`/api/v1/collect/pageview`, `/api/v1/collect/event`, `/api/v1/collect/heartbeat`) process synchronously in Express route handlers by directly invoking `CollectorService`, which performs synchronous read and write queries on Supabase (`visitors`, `sessions`, `page_views`, `events`).

**Bottlenecks at Scale**:
- Database roundtrips per individual HTTP request limit throughput.
- Transient network blips or database rate-limits cause immediate 5xx HTTP errors for client SDKs.
- Lack of in-flight queuing or batching.

---

## 2. QUEUE ARCHITECTURE
To decouple HTTP request reception from database write operations, an in-memory asynchronous Queue system (`IngestionQueue`) is introduced.

```
[SDK Client]
     │
     ▼ (HTTP POST / sendBeacon)
[Express Collector Route] ──► Validation Layer ──► Enqueue Item into IngestionQueue
                                                         │
                                                         ▼ (Return HTTP 202 Accepted)
                                                 [Ingestion Queue Buffer]
```

- **Data Structure**: High-speed bounded FIFO Queue.
- **Recovery**: Unprocessed queue items are flushed to disk or retried before process termination.
- **Observability**: Metrics track `queue_length`, `ingestion_rate_per_sec`, and `buffer_utilization`.

---

## 3. WORKER ARCHITECTURE
An asynchronous background worker (`QueueWorker`) periodically drains items from `IngestionQueue` on a configurable tick interval (e.g. every 500ms or when batch size hits 50 items).

- **Execution Flow**:
  1. Dequeues up to `BATCH_SIZE` items (default: 50).
  2. Groups items by target table (`page_views`, `events`, `sessions`, `visitors`).
  3. Executes single bulk multi-row `insert` or `upsert` queries to Supabase.
  4. Updates worker status and latency statistics in `PlatformMonitor`.

---

## 4. RETRY STRATEGY
If a bulk insert to Supabase fails due to temporary network disruption or rate-limiting:
1. The batch items are re-enqueued with an incremented `retryCount`.
2. Exponential backoff is applied:
   - **Retry 1**: 5 seconds delay
   - **Retry 2**: 15 seconds delay
   - **Retry 3**: 60 seconds delay
   - **Max Retries**: 5 attempts
3. If max retries are exceeded, failed items are recorded in the `FailedInserts` audit buffer for debugging without losing telemetry structure.

---

## 5. BATCH STRATEGY
- **Collector Server-side Batching**: Flushes when queue reaches `50 items` OR timer exceeds `500ms`.
- **SDK Client-side Batching**: Combines user interaction events (clicks, scrolls, navigation) in client memory queue and transmits in batches of up to `20 events` per request.

---

## 6. OFFLINE STRATEGY
The client tracking SDK (`public/tracker.js`) utilizes **IndexedDB** (`_pulse_offline_db`) for offline payload storage:
- When `navigator.onLine` is false or network fetches fail, events are saved into IndexedDB.
- When `online` event fires or app re-gains connection, the SDK flushes queued items sequentially using exponential retry.

---

## 7. COMPRESSION STRATEGY
- Express server enables `gzip`/`brotli` response compression.
- Client SDK uses compact payload keys (`u` for URL, `p` for path, `v` for visitor, `s` for session) with standard schema expansion on the Collector validation layer to minimize bandwidth overhead by ~60%.

---

## 8. IDEMPOTENCY STRATEGY
- Every payload generated by the SDK includes an `idempotencyKey` (`req_...`).
- The Collector validation layer maintains an LRU memory cache of processed `idempotencyKey`s with a 10-minute TTL.
- Duplicate payloads are safely acknowledged with `200 OK` but skipped during database enqueueing.

## 11. PLATFORM MONITOR SPECIFICATION
A dedicated system monitoring dashboard component (`PlatformMonitor`) that queries `/api/v1/monitor/stats` and displays real-time operational health:
- **Queue Metrics**: Queue length, active workers, batch processing time (ms).
- **Ingestion Velocity**: Events per second, requests per second.
- **Reliability Audit**: Retry queue count, failed insert count, dropped events (0).
- **Supabase Connectivity**: Response latency, active connection status.

---

## 12. RELIABILITY CHECKLIST
- [x] Zero data loss during temporary network disconnects (IndexedDB SDK backup).
- [x] De-duplication guaranteed via `idempotencyKey`.
- [x] Auto-recovery from Supabase connection drops via exponential backoff.
- [x] Reliable page termination tracking via `navigator.sendBeacon()`.
- [x] Adaptive heartbeat timer (30s active, 60s background, paused when hidden).

---

## 13. RISK ASSESSMENT & MITIGATION
| Risk | Severity | Mitigation |
| :--- | :--- | :--- |
| Server Crash / Process Restart | Medium | In-flight queue auto-flushes on process `SIGTERM`/`SIGINT`. |
| Database Connection Loss | High | Ingestion Queue buffers up to 10,000 requests in memory while worker retries with backoff. |
| High Traffic Burst | Medium | Non-blocking API routes immediately acknowledge request (`202 Accepted`) and buffer into worker pool. |
| Client Network Disconnect | Low | SDK persists events into IndexedDB and flushes automatically upon reconnection. |
